## 视频/音频导入卡顿问题排查（仅诊断，未改代码）

现象：安装版（NSIS 打包）里「视频转换」「音频转换」页导入素材会卡住数秒；VS Code 里跑则瞬间导入。

查证结论：
- **根因是 Tauri 同步命令阻塞主线程**。Tauri v2 官方口径：不带 `async` 的命令在**主线程**执行。
  - `src-tauri/src/lib.rs` 的 `pick_images` 是同步命令，内部 `mpsc::channel()` + `rx.recv()` 死等文件对话框，期间主线程完全不泵消息。
  - `ffprobe_video` 也是同步命令，内部 `Command::new(ffmpeg).output()` 同步等 105MB 的 ffmpeg 进程启动并退出。
  - `convert_video` / `convert_audio` 已经用了 `spawn_blocking`，唯独 ffprobe 漏了。
- `tauri-plugin-dialog` 2.8.3 的 `pick_file(s)` 内部是 `run_on_main_thread(...)`，`send_user_message` 在已是主线程时**内联执行**，所以不会死锁，但主线程仍被 `rx.recv()` 卡住整个对话框生命周期。
- 文件对话框默认 `parent = None`（项目代码也没调 `set_parent`），所以不存在跨线程模态窗的 EnableWindow 握手延迟。

实测排除项：
- `ffmpeg -i` 探测本身只要 **150~220 ms**（test/vidfmt 下多个格式），且把 ffmpeg.exe 拷到新目录模拟安装路径首次执行仍是 220 ms → **不是杀毒软件扫描、不是文件路径导致的**。
- 打包资源定位正常：dev 走 `target/debug/resources/ffmpeg.exe`，安装版走 exe 同级 `ffmpeg.exe`。

待修方案（已提交用户确认，尚未动手）：
1. `pick_images` / `pick_dir` 改 `async fn` + `tokio::sync::oneshot` 接收回调；
2. `ffprobe_video` 改 `async fn` + `spawn_blocking`；
3. 前端 `video-convert-page.js` / `audio-convert-page.js` 的 `loadEntry` 把「导入成功」与「探测信息」解耦，先启用 UI 再异步 ffprobe；
4. 可选：换成真正的 ffprobe 二进制，或给探测命令加 `-hide_banner`。
